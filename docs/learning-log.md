## 2026-08-04 MES 全类型终端与设备接入能力

### 学习问题
- “浏览器/PWA + 本地设备代理 + OT 边缘网关 + Java/Spring MES”能否覆盖扫码枪、PDA、工位屏、标签打印机、台秤、测试设备、PLC/IoT 设备和电子看板？

### 已知背景
- 这些终端与设备横跨人机交互、普通计算机外设、专业测试设备和工业控制系统，协议、实时性、安全责任与断网行为不同，不能全部按浏览器外设处理。
- 智能锁数字线程需要把扫码、重量、测试、设备程序、标签和看板事件关联到工单、工序、物料批次、固件版本与整锁 SN。

### 分析依据与明确假设
- 键盘仿真扫码枪可直接向浏览器输入；工业 PDA 可使用浏览器/PWA，厂商扫码服务通常还提供按键、Android Intent 或网络输出，复杂设备能力可能需要原生壳或厂商 SDK。
- 工位屏和电子看板适合使用浏览器/PWA/Kiosk；标签打印机、串口/USB 台秤和厂商测试设备通常通过本地代理、工控机服务或设备网关接入。
- PLC/IoT 应通过 SCADA、OPC UA 网关、MQTT Broker 或专用边缘适配器连接，不由浏览器直接读写 PLC，也不让 MES 承担毫秒级控制与安全互锁。
- OPC UA 提供平台无关、安全、建模、订阅和事件能力；Spring Integration 提供 MQTT 入站/出站适配能力，因此 Java/Spring 可承载接入管理与业务事件消费，但具体驱动仍取决于设备协议和厂商 SDK。
- 上述为行业通用架构，不代表目标企业设备已经支持这些协议；设备品牌、型号、驱动、点位、证书和写权限均待确认。

### 内容决策
- 采用四层接入：浏览器/PWA 负责交互，本地设备代理负责 PC 外设，OT 边缘网关负责 PLC/IoT/测试协议，Java/Spring MES 负责业务校验、状态机、追溯和审计。
- 设备原始高频数据保留在设备、SCADA、Historian 或边缘层；MES 只保存与制造业务相关的结果、关键参数、时间、会话 ID 和原始数据索引。
- 所有扫描、称重、测试和打印请求使用全局事件/命令 ID、设备 ID、工位 ID、SN、时间戳和结果状态实现幂等、应答、重试、未知态和离线补传；设备不得直接修改 MES 业务表。
- 标签打印区分首次打印与补打，测试结果使用唯一测试会话，PLC 使用命令块/状态块握手；浏览器、代理、网关与 MES 均需可观测和可追责。

### 验证与待确认
- 已依据 Zebra DataWedge、OPC Foundation、OASIS MQTT、Spring Integration，以及已有 Edge PWA/Web Serial/WebHID 官方资料核验整体可行性。
- 待建立企业工位—设备矩阵，逐项确认连接方式、厂商 SDK、是否需要下发、采样频率、业务关联键、断网缓存、超时状态、原始数据归属、网络区域与责任人。

## 2026-08-04 MES 工位端浏览器化与小团队实施策略

### 学习问题
- 企业没有专职前端和 Windows 开发团队，仅靠后端开发人员与 AI 辅助，能否实现 C#/WPF 客户端？
- MES 是否必须部署工位机客户端，能否采用纯 SaaS 浏览器应用？

### 已知背景
- 服务端团队以 Java/Spring 后端开发为主，新增 C#/XAML/WPF 会引入第二套语言、UI 框架、安装升级和 Windows 运维能力。
- 工位场景可能横跨“生产执行”“质量管控”“成品入库”，设备复杂度从键盘模式扫码枪、普通打印机到串口设备、标签打印机、烧录器、测试台和厂商 DLL 不等。

### 分析依据与明确假设
- C# 与 Java 在类型系统、面向对象、依赖注入和异步开发方面较接近，AI 可帮助生成 XAML、MVVM、接口客户端和安装配置，因此后端开发者能够完成边界清晰的 WPF 客户端；真正风险集中在 UI 状态、线程模型、外设生命周期、离线数据一致性、签名部署、自动升级和长期维护。
- 工位机不等于必须安装厚客户端。普通扫码录入、工单报工、检验、查询和看板可使用浏览器或 PWA；键盘仿真扫码枪通常可直接作为输入设备使用。
- PWA 可通过 Service Worker、Cache Storage 和 IndexedDB 支持前端缓存与一定程度的离线作业；Web Serial/WebHID 可在支持的 Chromium 浏览器中访问部分设备，但需要权限和兼容性治理，不能替代所有厂商驱动、Windows SDK、工业协议与安全控制。
- “纯 SaaS”若指所有运行与数据都依赖公网云端，则必须验证工厂网络、时延、断网持续生产、数据驻留和 OT 安全要求；浏览器 UI 与工厂本地边缘服务并不冲突，仍可保持核心业务 SaaS 化。

### 内容决策
- 推荐浏览器优先，不先建设完整 WPF 客户端：管理端和轻量工位使用 Web/PWA，共用 Java/Spring 服务端。
- 对串口、USB、标签打印、烧录、测试台、厂商 DLL 或长时间离线场景，增加职责单一的本地设备代理/边缘服务，通过受控的 localhost HTTPS/WebSocket 与浏览器通信，并负责本地队列、设备会话和补传。
- 只有在大量核心流程必须深度操作 Windows 外设、强离线或浏览器受限时，才建设 WPF 厚客户端；保持客户端轻量，业务规则、状态机和追溯判定仍归服务端，避免 Java 与 C# 两套业务逻辑漂移。
- 若必须采用 WPF，先选择一个硬件密集工位做纵向样板，验证扫码、打印、断网、重连、自动升级和远程诊断，再决定是否扩展到其他工位。

### 验证与待确认
- 已依据 Microsoft WPF、Edge PWA、离线存储/后台同步和 Edge Kiosk 官方文档，以及 Chrome Web Serial/WebHID 官方资料核验技术可行性。
- 待确认所有工位与外设矩阵、设备通信方式和厂商 SDK、标签打印精度与静默要求、最大断网时间、云端/厂内数据部署要求、Windows 版本和权限、客户端升级与远程支持方式。

## 2026-08-04 Windows MES 客户端技术栈选型

### 学习问题
- 当前 Windows 客户端常用哪些技术栈，应选择 C#/.NET 还是 Node.js 生态的 Electron？

### 已知背景
- 问题主要对应“生产执行”“质量管控”“成品入库”等阶段的工位客户端，可能需要扫码、标签打印、串口/USB 设备、文件访问、断网作业和自动升级。
- MES 服务端可继续采用 Java/Spring；客户端技术栈不必与服务端语言一致，双方可通过 HTTPS、WebSocket 或消息接口通信。

### 分析依据与明确假设
- 微软当前推荐 WinUI 3/Windows App SDK 用于新的 Windows 原生应用，同时继续支持成熟的 WPF 和适合业务表单快速开发的 WinForms。
- Electron 将 Chromium 和 Node.js 随应用打包，允许使用 JavaScript/TypeScript、HTML、CSS 维护 Windows、macOS、Linux 共用代码，但安装体积、内存占用、安全更新和 Node 权限隔离需要额外治理。
- Tauri 使用系统 WebView 和 Rust 宿主，可复用 Web 前端并减小安装体积，但团队需要接受 Rust、WebView 差异和插件生态评估；Avalonia 可作为 C#/.NET 跨平台桌面方案。
- 上述为当前通用选型参考，不代表企业已有 Windows 版本、外设驱动、安装权限、网络隔离或自动升级条件已经确认。

### 内容决策
- Windows 专用、外设集成较多、强调长期稳定和离线能力的 MES 工位端，优先评估 C#/.NET；存量和重业务场景优先 WPF，追求现代 Windows 体验的新项目可评估 WinUI 3。
- 已有成熟 TypeScript/Vue/React 团队、需要跨平台或希望复用 Web 页面时，可选择 Electron；必须关闭不必要的 Node 集成、启用上下文隔离与沙箱、限制导航和 IPC，并持续更新 Electron/Chromium。
- 对只需要扫码录入和普通打印的场景，优先评估浏览器/PWA；不要为了“客户端化”增加安装、升级和安全维护成本。
- 推荐总体边界为“Java/Spring MES 服务端 + C# 工位客户端或受控 Web 容器 + 独立设备适配层”，不把 PLC 安全互锁或毫秒级控制放入桌面客户端。

### 验证与待确认
- 已依据 Microsoft Windows App SDK/Windows 开发官方文档、Electron 官方架构与安全文档、Tauri 和 Avalonia 官方资料核验当前技术路线。
- 待确认目标 Windows 版本、是否只运行 Windows、工位外设清单及厂商 SDK、断网时长与补传规则、安装/签名/升级权限、内存和磁盘限制、前端与 C# 人员结构。

## 2026-08-04 MES 开发语言与 Java/Spring 技术栈适用性

### 学习问题
- 市面上的 MES 是否存在统一的开发语言要求，Java/Spring 技术栈能否用于 MES 建设？

### 已知背景
- 学习者为 Java 全栈开发，关注智能锁离散制造八阶段中的工单、排产、物料、过站、质量、入库和追溯能力。
- MES 既可能是企业自主建设的系统，也可能是采购的商业套件；“使用系统”“通过接口集成”和“进入厂商平台内部二次开发”是三种不同场景。

### 分析依据与明确假设
- ISA-95 定义制造运营活动、数据模型和企业层与制造层接口，属于技术无关的参考架构，并不规定 MES 必须采用 Java、C# 或其他语言。
- 自研 MES 可按团队能力和非功能需求选择技术栈；商业 MES 的内部实现语言由厂商决定，普通外部集成通常取决于 REST/Web Service、消息、文件、数据库或工业协议接口，而厂商插件、脚本和低代码扩展可能限定语言与工具链。
- Spring 生态具备 HTTP、JDBC、JPA、JMS、Kafka、AMQP、MQTT 等集成能力；Java 也可通过 Eclipse Milo 接入 OPC UA，因此适合 MES 业务服务与非硬实时设备集成。
- 上述为行业通用判断，不代表目标企业或指定厂商产品已经开放相同接口；产品版本、授权、部署环境、SDK 和二开限制均待选型时确认。

### 内容决策
- 明确结论：MES 没有行业统一的编程语言要求，Java/Spring 可以作为自研 MES 的主技术栈。
- 将 Java 边界限定在业务事务、状态机、接口、追溯、权限审计和设备会话；PLC 扫描周期、运动控制、急停及安全互锁继续由控制器、设备程序或实时组件承担。
- 选型时不只询问“产品是什么语言写的”，还要核验开放 API、事件/消息能力、设备协议、插件语言、SDK 版本、离线机制、升级兼容、授权和厂商支持。

### 验证与待确认
- 已依据 ISA 官方对 ISA-95 技术无关性的说明、Spring Boot 与 Spring Integration 官方文档，以及 Eclipse Milo 官方项目资料核验结论。
- 待确认企业采用自研还是商业 MES、是否需要进入厂商内核二开、目标设备协议、网络隔离与离线生产要求、数据库和中间件限制、团队运维能力及产品授权条款。

## 2026-08-04 MRP 与 MES 的职责边界

### 学习问题
- MRP（物料需求计划）一般是否由 MES 处理？

### 已知背景
- 问题位于八阶段主线的“计划排产”和“物料齐套”，其输入还涉及“销售需求”以及“产品与工艺准备”中的 BOM、版本等基础数据。
- 企业场景为智能锁离散制造；需求可能来自销售订单或预测，物料包括主板、指纹模组、电机、电池组件、结构件、包装材料等。

### 分析依据与明确假设
- 按行业常见边界，MRP 需要综合需求、BOM、库存、在途/在制、提前期和批量规则，通常属于 ERP 的计划管理能力；部分企业可能由 APS 或一体化平台承担相关计算。
- MES 通常接收已下达或已释放的生产工单、物料需求与版本约束，负责车间执行、工序派工、领料/投料校验、消耗与报废反馈，而不是企业级 MRP 的主责系统。
- 上述为行业通用模型，不代表本企业已经采用相同系统分工；实际系统产品、库存口径、计划层级和接口责任均待确认。

### 内容决策
- 明确区分“算哪些物料、何时需要”的 MRP 与“现场是否齐套、实际投了什么”的 MES 物料执行。
- 用“ERP/APS 计划—MES 执行—WMS 库存作业—MES/ERP 实绩闭环”解释跨系统关系，避免把 MES 中的缺料检查、线边补料或物料配送误称为完整 MRP。

### 验证与待确认
- 已形成当前学习结论：一般由 ERP 运行 MRP，MES 以消费计划结果和反馈实际执行为主；带有 MRP 功能的 MES 套件属于产品或企业架构差异，不能据此泛化。
- 待确认企业当前 ERP/MES/APS/WMS 产品、MRP 运行位置与频率、库存数据主权、工单下达规则、缺料处理和紧急插单后的重算机制。

## 2026-07-29 全局英文缩写释义治理

### 学习问题
- 当前 MES 与工业自动化内容中存在大量 ERP、MOM、SCADA、PLC、OPC UA、MQTT、BOM、NCR 等缩写，学习者无法仅凭字母理解英文原词、命名逻辑和实际含义。
- 如何让所有 Markdown 与静态页面中的缩写既能就地理解，又能进入独立页面学习“为什么这样定义”？

- 项目现有 MES 八阶段、模块、岗位、系统、Java 专题和 ISA-95 工业自动化体系，共 55 个入口与详情页面需要统一治理。
- 部分术语是标准首字母缩写，部分是历史名称或品牌名称；不能为 ISO、MQTT、Modbus 等名称强行编造逐字母展开。

### 分析依据与明确假设
- 先全局扫描 HTML 与 Markdown 的大写术语，再依据标准组织、协议组织或权威产品说明核实英文全称。

- 企业自定义缩写、字段码和产品型号不纳入行业词典，仍需由企业数据字典确认。

### 内容决策
- 新建统一英文缩写词典 Markdown 和静态学习页，并从全局页面提供入口。
- 首次出现和高频出现的缩写不只给中文简称，还需要明确英文全称；非首字母缩写明确标注“专名/历史名称”。
- 为防止术语漂移，新增自动化检查，验证词典覆盖、HTML 语义和内部链接。

### 验证与待确认
- 已全局扫描 Markdown 与 HTML 中的大写术语，统一词典覆盖 94 个标准、系统、业务、质量、通信和控制术语。
- 已为 56 个现有学习页面加入静态词典入口，并生成 1,512 处 `abbr` 语义释义；桌面端可悬停查看英文全称和中文含义，触屏端可进入完整词典阅读命名原因。
- 已核验并明确：ISO 不是首字母缩写；OPC 由历史上的 OLE for Process Control 演进为 Open Platform Communications；MQTT 的 OASIS 委员会名称与现代发布/订阅语义不能机械等同；Modbus 是协议专名。

- 待确认企业内部缩写、厂商设备型号、字段缩写和公司专有英文命名。

## 2026-07-29 ISA-95 与工业自动化体系学习文档

## 2026-07-29 Java MES 与生产设备开发边界

### 学习问题
- Java 开发 MES 时，是否还需要开发生产机器，以及 MES、设备系统、PLC、设备程序和嵌入式软件之间如何分工？

### 已知背景
- 企业场景为智能锁离散制造，现场可能包含扫码器、标签打印机、扭矩工具、固件烧录设备、功能测试台、视觉检测、老化设备和自动化装配线。
- 学习者岗位为 Java 全栈开发，重点是 MES 业务系统和设备集成，不预设同时承担自动化、电气或嵌入式岗位。

### 分析依据与明确假设
- 行业中通常由设备/自动化团队负责 PLC、运动控制、安全互锁、设备驱动和实时控制，MES Java 团队负责业务上下文、设备接口、采集会话、结果判定与追溯。
- 若企业已有 SCADA、IIoT 平台或边缘网关，Java MES 可能只对接统一平台；若设备仅提供 TCP、串口或厂商 SDK，则可能需要开发设备适配器或边缘采集服务。
- 实际设备协议、网络区划、程序下发权限和异常责任人为待确认事实。

### 内容决策
- 将“生产机器开发”区分为机器控制开发、设备接入开发、MES 业务开发三层，避免把设备对接误解为使用 Java 编写 PLC 或机器固件。
- 智能锁案例优先说明烧录机、功能测试台、扭矩工具、扫码器和标签打印机与 MES 的会话及数据交互。
- Java 关注点包括协议适配、会话关联、幂等重发、超时未知态、离线缓存、版本校验、安全、监控和可追溯证据。

### 验证与待确认
- 待确认企业是否已有设备网关/SCADA、设备支持的协议、哪些工位允许 MES 下发参数、原始数据保存位置及断网生产策略。
