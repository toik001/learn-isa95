FOUR LAYERS

把需求翻译成实现约束

层开发者要问产出
业务谁在什么条件下做什么，成功/失败/撤销如何定义？用例、命令、责任与异常流程。
数据哪些是实体、关系、版本、快照和不可变量？聚合、状态、唯一约束和审计模型。
系统权威来源是谁，哪些复制，何时同步，失败谁补偿？接口契约、事件和对账责任。
实现并发、重试、事务、权限、观测和历史复现怎么保证？代码、测试、迁移、监控和运行手册。

IMPLEMENTATION

横贯八阶段的八个关注点

领域状态机

显式命令与守卫；状态、原因和业务动作一一对应。

幂等

事件 ID 防技术重复，业务唯一约束防语义重复。

并发

乐观锁、条件更新、库存预留和唯一有效关系。

事务消息

本地事务 + Outbox，消费端 Inbox/去重，失败可重放。

跨系统补偿

Saga、冲销、重试、人工接管和持续对账。

权限审计

最小权限、职责分离、前后值、理由、电子签名和附件。

时间版本

业务时间/接收时间/有效时间；历史引用不可变发布 ID。

追溯读模型

来源、关系、有效期、查询深度、数据水位和隐私。

FRONTEND

前端不是“把按钮放出来”

  • 状态可解释显示当前状态、可执行动作、不可执行原因和下一责任人。
  • 差异可比较版本/变更逐字段展示旧值、新值、范围和影响对象。
  • 扫码反馈区分成功、重复成功、业务拒绝、网络未知和待确认，避免盲目重扫。
  • 证据钻取指标、工单、SN 和异常能逐层回到原始事实与来源系统。

DIAGNOSIS

出现“数据不一致”时的诊断顺序

  1. 先定义正确事实

    不要先手改数据库；明确实物、业务和系统各自应是什么。

  2. 定位权威来源

    区分来源系统错误、复制延迟、重复/乱序或补偿未完成。

  3. 按业务键对齐日志

    串联命令 ID、事件 ID、来源 ID、版本、Trace ID 和时间。

  4. 选择恢复动作

    重放、冲销、补偿或授权修复，保证重复执行安全。

  5. 补监控与测试

    把这类不一致变成可自动发现的对账和回归用例。

SELF CHECK

问题 2

问题 3
