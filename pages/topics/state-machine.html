TOPIC 02 · STATE MACHINE

领域状态机

状态机用来保护业务事实的合法变化：谁在什么条件下执行什么命令，从哪个状态到哪个状态，并留下什么副作用和证据。

元素：状态 / 命令 / 守卫 / 事件原则：后端强制反模式：直接 update status

本页导航

  • 建模
  • 正交状态
  • 失败路径
  • Java 设计
  • 测试
原则状态名称来自业务事实；不要先选状态机框架，再把所有字段硬塞进一个流程。

MODEL

一个完整迁移需要六项

当前状态

命令发生前可验证的业务事实。

命令

带意图的动作，如下达、冻结、放行、取消。

操作者

角色、权限、组织范围和必要电子签名。

守卫

版本、数量、前序、质量、设备、库存等前置。

新状态

命令成功后形成的新业务事实。

副作用

事件、任务、预留、审计或补偿；需与状态一致。

ORTHOGONAL STATES

不要用一个状态表达所有维度

对象维度示例
整锁 SN制造加工中 / 已完工。
整锁 SN质量待检 / 冻结 / 已放行。
包装单元包装开放 / 封箱 / 已拆箱。
库存单元仓储待接收 / 已上架 / 已分配 / 已出库。

把这些维度分开后，用跨维度守卫表达“只有制造已完工且质量已放行且包装已封箱，才可入库”。

FAILURE PATHS

状态机必须有返回与终止路径

  • 缺料“部分齐套”可回到缺料处理中或进入已齐套，也能取消/关闭未解决。
  • 复验再次失败回到重新评审，再决定新处置或关闭，不无限循环。
  • 发货重新分配返回待分配，也可取消/关闭。
  • 接口未知结果使用“待确认”，不要用失败或成功掩盖未知。

JAVA DESIGN

推荐实现

  • 领域命令Order.release(command) 内验证状态和不变量，返回领域事件。
  • 乐观锁聚合版本阻止并发迁移；冲突让调用方重新读取而非静默覆盖。
  • 数据库约束唯一有效绑定、非负数量等关键不变量不能只靠 Java if。
  • 状态历史保存 from/to、命令、原因、操作者、业务时间、版本和关联单据。
  • Outbox状态迁移与事件同事务，避免新状态已提交但事件丢失。
  • 前端能力后端返回允许动作和拒绝原因，前端只做引导不做最终授权。

TEST

测试策略

  • 每个合法迁移成功并产生正确事件
  • 每个非法来源状态被拒绝且无副作用
  • 守卫边界值与权限组合
  • 并发两个命令只有一个成功
  • 重复命令返回相同结果或明确冲突
  • 所有非终态存在进展、返回或终止路径
