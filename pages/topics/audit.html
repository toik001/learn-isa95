TOPIC 05 · AUTHORIZATION & AUDIT

权限与审计

MES 审计要证明“谁基于什么授权、在什么业务上下文、把什么从什么改成什么、为何修改、产生了什么后果”，而不只是记录登录日志。

原则：最小权限控制：职责分离证据：前后值 + 理由 + 关联对象

待确认岗位、组织、审批矩阵、电子签名与数据保留需按企业制度和适用法规确认。

AUTHORIZATION MODEL

权限至少有四个维度

功能

查看、创建、下达、改判、放行、导出等具体动作，而非只有菜单访问。

数据范围

工厂、车间、产线、仓库、产品族、客户和供应商范围。

对象状态

草稿可编辑，已发布只能修订；执行中/已关闭对象需要更高权限。

业务条件

金额/数量、质量严重度、追溯范围、是否本人创建等动态约束。

HIGH-RISK ACTIONS

应单独建权和加强证据的操作

操作风险控制建议
跳站 / 补录制造证据失真限定对象、双人复核、理由和附件。
解绑 / 换件追溯关系断裂关闭旧关系、引用返工/NCR、保留前后值。
质量改判 / 特采 / 放行缺陷逃逸职责分离、电子签名、范围快照。
库存调整 / 解冻账实不符或错料盘点证据、审批、冲销引用和对账。
固件发布 / 手工选择错版与安全风险发布签名、适用范围、双人审批。
追溯导出 / 客户信息隐私泄露用途、脱敏、下载水印、有效期与审计。

AUDIT RECORD

一条可用审计记录

Actor

谁

用户/服务身份、角色、组织、认证强度、代理/委托关系和来源终端。

Context

在哪个上下文

工厂、工位、工单、SN、单据、Trace ID、IP 和业务时间。

Change

改了什么

命令、对象、旧值、新值、对象版本、状态迁移和受影响数量。

Reason & Evidence

为什么

原因码、说明、关联审批/NCR/返工、附件哈希、结果和失败码。

JAVA DESIGN

实现建议

  • 服务端授权方法/命令入口按动作和数据范围校验，不能依赖前端隐藏按钮。
  • 策略集中RBAC 提供基础角色，ABAC/领域守卫处理工厂、状态和数量条件。
  • 审计同事务业务变更与审计事件同事务落库；审计表只追加，限制修改/删除。
  • 敏感数据日志不记录密钥、完整客户联系方式和固件签名私钥；必要字段脱敏。
  • 电子签名高风险批准重新认证并绑定本次内容摘要，避免签名后内容被换。
  • 可检索性按对象 ID、SN、工单、用户、命令和时间建立索引与导出权限。

TEST

权限与审计测试

  • 角色能否访问不属于本工厂的数据
  • 前端绕过后后端是否仍拒绝
  • 创建者是否能自批高风险决定
  • 并发批准是否只有一个有效结论
  • 审计是否保存真实前后值而非 DTO
  • 失败操作是否记录原因但不伪造变更
  • 导出是否脱敏、限时和可追责
  • 签名内容改变后是否失效
