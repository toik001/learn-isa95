幂等与并发

扫码会重扫、设备会重发、消息会重投、用户会双击；MES 必须让同一业务意图重复执行仍只产生一次有效事实，同时阻止不同意图争抢同一资源。

防技术重复：事件 ID防业务重复：唯一键防并发覆盖：版本 / 条件更新

原则“接口不报错”不是幂等；重复请求必须返回同一个业务结果，而且不能重复扣料、绑定、过站或发消息。

TWO LAYERS

事件 ID 与业务唯一键缺一不可

技术去重

请求/事件 ID 识别同一传输重试，保存首次响应；适合网络超时、消息重投。

业务唯一

即便事件 ID 不同，也不能重复发生同一事实，如 SN + 工序 + 有效成功、子件 SN 的有效绑定。

例：终端因超时生成相同事件 ID 重发，技术去重返回首次结果；操作员又重新扫码生成新事件 ID，业务唯一约束仍阻止第二次有效过站。

PATTERNS

典型 MES 场景

场景幂等键 / 并发点保护方式
工单下达来源工单 ID + 版本唯一索引，旧版本拒绝。
SN 过站事件 ID；SN + 工序 + 业务尝试去重表 + WIP 条件更新。
关键件绑定子件 SN 的唯一有效关系部分唯一索引/锁定子件。
库存分配需求行 + 库存单元；可用数量条件更新或预留行锁。
设备结果测试会话 ID + 序号去重、排序、状态守卫。
完工回传工单 + 完工批次/业务事件凭证唯一，重复返回原凭证。

RESULT SEMANTICS

前端要区分五种结果

首次成功

本次创建事实，返回业务 ID 与新状态。

重复成功

事实此前已由同一意图完成，返回原结果并标明重复。

业务拒绝

状态、版本、资格或规则不允许，返回可解释原因。

并发冲突

其他意图已改变对象，要求重新读取后决定。

结果未知

超时但服务端是否提交未知，应查询同一事件 ID，而非新建意图。

JAVA DESIGN

实现建议

  • Inbox 表event_id 唯一，保存处理中/成功/失败和序列化结果；处理中并发请求等待或返回处理中。
  • 唯一约束优先用数据库约束收口竞态，捕获冲突后查询原事实并判断重复还是冲突。
  • 条件更新update ... where id=? and state=? and version=?，行数 0 触发重新判断。
  • 锁粒度锁聚合/库存单元而非全表；按固定顺序锁多个对象防死锁。
  • 结果留存幂等窗口覆盖设备离线和消息最大重试期，过期策略不能破坏业务唯一。
  • 乱序保护版本、序号和业务时间共同判断；旧事件入隔离队列而非覆盖新状态。

TEST

测试策略

  • 100 个相同请求只有一次副作用
  • 不同事件 ID 的同一业务事实仍只成功一次
  • 并发分配不会产生负库存
  • 超时重试返回首次业务 ID
  • 乱序设备结果不倒退状态
  • 事务失败后幂等记录不误标成功
